01 Where things stand

Two solid halves that need marrying

This isn't a blank-page rewrite. You already have both of the hard pieces — they just haven't been introduced to each other yet. One half does the thinking; the other drives the hardware. The whole project is the bridge between them.

The brain to bring across

mazerunner-core — mature, header-only C++

  • 16×16 flood-fill maze solver
  • Trapezoidal motion profiles
  • Forward / rotation PD controllers
  • Search, wall-follow & calibration behaviour
  • Serial CLI & telemetry reporting

The body already working

Your E4 CubeIDE project — HAL drivers

  • Both encoders in hardware timer mode
  • 4-channel motor PWM on one timer
  • SSD1306 OLED talking over I²C
  • MPU-9250 gyro talking over SPI
  • ADC, Bluetooth UART, buttons & LEDs

The fiddly, get-stuck-here work — hardware quadrature decoding, landing four PWM channels on one timer, bringing up SPI and I²C peripherals — is done. What remains is mostly C++ structure and wiring things together, which is much closer to familiar ground.

02 Target architecture

One boundary holds the two languages apart

The generated HAL stays as C, so CubeMX can still regenerate it. Everything you write lives in C++ above an extern "C" boundary. The logic layer never touches a register — it calls a thin wrapper class, and the wrapper calls your HAL driver.

04 Sequenced roadmap

Seven phases, each one runnable

Ordered so the robot does something real at the end of every phase, and so nothing depends on the greenfield sensing work until it has to. Each phase names what "done" looks like, so you always know where the line is.

P0

Stand the project up as C++ ✓ complete

Switch the CubeIDE project to a C++ toolchain, wrap the CubeMX/HAL includes in extern "C", and settle the folder split: generated HAL stays C, your app and logic become C++. Along the way we cleared four latent bugs: constants defined in config.h (split into config.c), eight headers missing or mis-typed C++ guards, and a const-correctness issue in the OLED driver.

Done: builds green as mixed C/C++ with the entry point in app_main.cpp, confirmed running on the mouse — live OLED, encoders, battery and motors.
P1

Bring the brain across

Port the hardware-independent classes — maze, queue, profile, motion, mouse, reporting — with their hardware calls stubbed. This is the bulk of the code and it moves almost intact.

Done when: the maze solver compiles and a flood-fill can be exercised over the Bluetooth CLI, off the robot.
P2

Wire the wrappers to your drivers

Fill in Encoders, Motors, Battery, and the control-loop tick against the HAL drivers you already have. Now the logic layer can actually move the robot.

Done when: a commanded profile drives the wheels and the encoders report distance & angle back.
P3

Build the wall sensing

The one block written from scratch: pulse the emitters, DMA-scan the receiver channels, subtract dark from lit, and expose it behind the same sensor interface the logic expects. Add the calibration routine.

Done when: live wall readings drive the steering feedback and left/right/front wall detection works.
P4

Fold in the gyro

Read the MPU-9250 each tick and feed its angle and rate into the rotation and steering controllers, alongside — or in place of — the encoder-derived angle.

Done when: turns hold their angle using the gyro, noticeably steadier than encoders alone.
P5

Build the menu & launcher

Pick up where you left off: OLED menu, encoder wheel as the cursor, buttons as OK / Cancel — the on-robot way to choose and start each routine.

Done when: you can scroll to a routine and launch it from the screen, no serial needed.
P6

Persistence & tuning

Store the solved maze to the I²C EEPROM and reload on boot, then tune the config constants — wheel diameter, mouse radius, controller gains, feed-forward — on the real robot.

Done when: the maze survives a power cycle and the robot searches to the goal and back.

05 Open items & decisions

Things to settle before they bite

The hardware all checks out — these are choices to make up front, not problems to fix. Deciding each one early is cheap; discovering it at link time or mid-tune is not.

decided

Control loop runs at 1 kHz

Chosen over mazerunner's 500 Hz — it suits the gyro and the F411 has huge headroom. It also lands neatly on the project's existing 1 ms SysTick, so the control update just runs every tick. LOOP_FREQUENCY = 1000 and LOOP_INTERVAL = 0.001 propagate through most of the rate-dependent maths automatically; the controller gains (the D terms especially) get re-tuned on the robot in Phase 6.

your call

Encoder resolution — ×2 or ×4

The timers are set to count one edge (TI1, ×2). Switching to both edges (TI12, ×4) doubles your odometry resolution for free — a small config change now, well worth taking.

note

A couple of C++ housekeeping points

The header-only classes each need exactly one translation unit that instantiates them, and mazerunner's file-scope const config values want care so they don't multiply-define across units. Both are routine — just decided up front, not discovered at link time.

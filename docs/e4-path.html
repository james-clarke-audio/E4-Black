E4 Micromouse · route decision

Choosing the Path

How the mouse decides where to go next. Not how the maze is solved — that is the flood, and it is going to be replaced — but the layer above it: what turns a solved maze into wheel movement, and why there is currently no such thing as a planned route.

The short answer: there is no path generator. No list of commands is ever built, and there is no speed-run mode. The mouse re-solves the entire maze at every cell boundary and takes one step down the gradient. The "plan" only ever exists as a cost map, and it is thrown away and rebuilt 170 mm later.

This is worth stating plainly because it is the opposite of the architecture most people expect. There is no path[], no "FFRLFF" string, no compile step between knowing the maze and driving it. Every decision the mouse makes is made fresh, from scratch, at the moment it has to be made.

Where the decision happens

All of it lives in one loop, Mouse::search_to(Location target) in mouse.h. One pass of the loop covers exactly one cell.

The loop does not begin at the cell centre. It begins at the sensing position — SENSING_POSITION = 170 mm into a 180 mm cell, i.e. 10 mm before the far boundary. That is the last moment at which the walls of the next cell can be read while there is still room to act on them.

  1. Commit to the next cell m_location = m_location.neighbour(m_heading) — she updates her belief before she has finished arriving. From here on the "current cell" is the one she is entering.
  2. Read and record the walls sensors.update() then update_map(), which writes three wall states (left, front, right) relative to her heading. update_wall_state only writes a wall that is still UNKNOWN — a wall seen once is never revised.
  3. Assert the goal room maybe_assert_goal_room(). On first entry to the centre 2×2, all twelve of its wall segments are filled in at once from the one-entrance rule, rather than driving all four squares.
  4. Re-flood the whole maze maze.flood(target) — every cell's distance to the target, recomputed from nothing.
  5. Pick a neighbour maze.heading_to_smallest(m_location, m_heading) returns the absolute compass heading of the cheapest reachable neighbour, or BLOCKED.
  6. Convert to a relative move hdgChange = (newHeading - m_heading) & 0x3 turns an absolute heading into one of four relative directions, and a switch dispatches the motion.

That is the entire path-decision mechanism. Six steps, no state carried between them beyond the map itself.

The flood

A breadth-first fill outward from the target, not from the mouse. Every reachable cell ends up holding its step-count distance to the goal; unreachable cells stay at MAX_COST.

m_cost[target] = 0;  queue.add(target);
while (queue.size() > 0) {
  here    = queue.head();
  newCost = m_cost[here] + 1;
  for (heading : NORTH, EAST, SOUTH, WEST)
    if (is_exit(here, heading))
      if (m_cost[neighbour] > newCost) {
        m_cost[neighbour] = newCost;
        queue.add(neighbour);      // frontier
      }
}

Because the fill runs from the target outward, the mouse never has to search for a route at all. It only has to look at its four neighbours and step to whichever number is smallest. The route is implicit in the gradient, which is exactly why no path list is needed and why re-flooding every cell costs nothing conceptually — a newly-discovered wall simply reshapes the numbers before the next decision is taken.

The tie-break is the only route shaping there is

When several neighbours share the lowest cost — which happens constantly, since any open area has many equally-short routes across it — something has to choose. That something is the order of comparison inside heading_to_smallest:

best_cost = cost(cell);
next = start_heading;              // ahead
if (neighbour_cost(...) < best_cost) ...
next = right_from(start_heading);   // then right
next = left_from(start_heading);    // then left
next = behind_from(start_heading);  // then behind

The comparison is a strict <, so a later candidate can never displace an equal earlier one. The effect is a fixed preference order: ahead, then right, then left, then back.

This matters more than it looks. Preferring "ahead" is what stops her staircasing across open ground — she runs the straight to its end and turns once, instead of alternating turn-turn-turn for the same cell count. Every straight she does run is a straight this tie-break chose for her. It is the closest thing in the codebase to a route optimiser, and it is four lines of ordering.

Upstream's own comment notes this could be extended to look ahead and then toward the goal. It is a reasonable first place to experiment, and it changes route shape without touching anything else.

The move vocabulary

Four moves. That is everything the mouse can do between one decision and the next.

DirectionCallWhat actually happens
AHEADmove_ahead()adjust_forward_position(-FULL_CELL) then wait for SENSING_POSITION. It does not move her — it re-bases the odometry origin back by one cell and lets the existing motion carry on. She never stops.
RIGHT / LEFTturn_smooth()A curve at constant forward speed. Waits for the turn point, runs a rotation profile while forward speed is held, then relabels the position frame by exit_offset. Also never stops.
BACKturn_back()The only move that halts: coast to the cell centre, spin 180° in place, drive back out to the sensing point. Reserved for dead ends.
So she is already continuous everywhere except a dead end. There is no "search speed vs run speed" gear change to add, because there is no stopping to eliminate — a search run is one unbroken motion from the start cell to the goal. What a speed run would add is not smoothness, it is magnitude: longer straights taken faster because the cells ahead are known.

One in-place turn detail worth knowing: turn_IP180() keeps a static int direction and flips sign on every call, so consecutive 180s alternate CW/CCW. That is deliberate — it stops a long search from winding the tether one way all afternoon.

Open and closed: the two ways to read the same map

A wall has four states, and two of them matter here: WALL, EXIT, and crucially UNKNOWN. The mask decides how an unknown wall is read.

MaskUnknown wall is…Used for
MASK_OPENan exitSearching. She assumes she can get through anything she has not looked at, which is what makes her willing to explore. Set by maze.initialise() and left alone.
MASK_CLOSEDa wallA route guaranteed drivable, because it only crosses cells she has actually seen. Currently used for reporting only.

This is the single most important distinction for anything built on top, and it is already implemented and working. An optimistic flood gets her exploring; a pessimistic flood gets her a route she can commit to at speed. The machinery for both exists today.

Why there is no speed run

Since this was written, the machinery for one exists. Ch 12 builds the time-weighted planner and both diagonal methods. What follows here is still true — nothing drives them, so there is still no speed run — but the reasoning below about what one would be built from has been overtaken by what was actually built.

Because upstream does not have one either, and the port inherited the gap honestly.

ukmars' mazerunner-core declares the function and leaves it empty:

// mazerunner-core/mouse.h, upstream
void run_to(Location target) {
  (void)target;
  //// Not implemented
}

with a long comment above it describing what it ought to do — including the observation that the path may be either pre-calculated into a series of operations, or computed on the fly from the cost map. Upstream's README is blunter still: the code, it says, "makes no attempt to do things like run faster through known sections", and leaves that to the user.

The E4 port did not even carry the empty stub across. There is no run_to in mouse.h at all. The State enum does declare INPLACE_RUN and SMOOTH_RUN — but that enum is declared and never referenced anywhere in the firmware, in the port or upstream. It is a statement of intent, not a mechanism.

What a speed run would be built from

More of the groundwork exists than the empty menu entry suggests. Three of the four pieces are already written and tested.

A safe route over known cells exists

maze.set_mask(MASK_CLOSED) then maze.flood(goal())
— never crosses an unseen wall

A path generator exists, mis-wired

report_best_route() walks START → goal by calling
heading_to_smallest repeatedly. That IS pathgen —
it just emits "SP,x,y" to the app instead of motion.

Turn geometry, indexed exists

turn_params[4] keyed by TurnType, already bench-tuned
for the E4 arc (R ~ 100 mm at 300 mm/s)

Multi-cell straights at speed missing

the motion layer can only do one cell at a time;
nothing run-length-encodes "straight × 6" into a
single accelerate / cruise / decelerate profile

So the shape of the work is: take the cell list that report_best_route() already produces, run-length-encode it into straights and turns, and give the motion layer a way to execute a straight of n cells as one profiled move rather than n re-bases. The decision-making is done; it is the execution that is single-cell-bound.

The one real trap. Everything in search_to re-derives position from the cell it is entering, 170 mm at a time, and re-anchors on the walls each cell. A multi-cell straight gives up that re-anchoring for its whole length. At search speed the drift over one cell is nothing; over six cells at run speed it is the whole error budget. That is the reason a speed run is a different problem from a fast search, and not just a bigger number in the config.

How fast may she cross a cell?

Searching, she crawled at SEARCH_SPEED from the first cell to the last. That is right for ground she has not seen — she is reading walls and deciding at every cell — and it is waste everywhere else. “Everywhere else” is most of the way home, because the return leg is ground she has just driven.

But the test is PER CELL, not per leg. The obvious version is to run the whole return leg fast because she has just driven it. That is wrong: the flood picks the best known path home, and known does not mean visited. She will have seen a cell’s walls from next door without ever entering it, and those cells are exactly where there is still something to learn. The return leg is an exploring run that happens to be quick in the parts already covered.

cruise_speed() is that rule, in one place, used by the driven search and the simulated one so neither models something the other does not do:

conditionspeed
cell she is entering is fully visited, and the move out of it is straightRUN_SPEEDnothing to sense, no turn to arrive at too fast
anything elseSEARCH_SPEEDsomething to learn, or a turn coming

The second condition is the one that is easy to forget. There is no room to shed speed between a cell’s sensing point and the turn point that follows it, so carrying run speed into a turn means entering it too fast. Checking costs nothing: in visited territory the map is complete, so heading_to_smallest() on the flood she already has is a reliable one-cell look ahead.

A sloppy read at speed cannot hurt her, and that is what makes this safe rather than merely fast. She still senses and still calls update_map() in a cell crossed at 600 mm/s — but update_wall_state() returns early unless the wall is still UNKNOWN, and fully visited means every wall in that cell has been decided. So a bad reading is discarded by construction, in exactly the cells where the rule permits speed. The one place a wrong wall could be written is a cell with something unknown in it — and those are the cells she is required to crawl through.

The wall follower stays at search speed throughout, deliberately: cruise_speed() reads the flood to look ahead, and a follower never floods — it would be reading whatever costs an earlier run left behind.

The wall follower is a different competition

Keep one hand on the wall and walk. No map, no memory, no flood. It is the oldest maze algorithm there is, and it is easy to file it as a weaker solver kept around for diagnostics — which is wrong, and was wrong in this repository’s own comments until it was corrected.

A wall-follower course is built with a wall connected all the way to the centre, so a follower always arrives. That is the point of the event. A maze-solver maze is built the other way round, with the inside deliberately disconnected from the outside, so a follower can never reach the middle of one however long it walks. Same code, two events.

Which makes the numbers worth having. Running a follower over every file in mazefiles/binary:

outcomefiles

The same 90 for both hands, with not one maze yielding to one hand and not the other. That is structural rather than luck: the hand decides which route she walks, not whether the centre is reachable at all. If the centre’s walls are connected to the perimeter, both hands are walking the same wall component and both get there; if it is an island, neither can.

Five of the 90 are built for the class explicitly — uk2010follower, uk2011follower-final, tic05followersheats, robotic-2011-follower-heats and -finals — and 33 are competition mazes, including japan1991, uk2003q and uk2009f. test3.maz arrives in 14 cells, which makes it the fastest smoke test in the corpus.

FOLLOW_STEP_LIMIT is not a guard against a weak algorithm. On its own course it never trips. It exists because the same code gets pointed at a solver maze in the simulator, where not arriving is the correct answer — and the only wrong behaviour would be walking for ever while that answer is true. 512 cells, four times the arena, then WF,gave up after N cells.

She maps while she follows, so even a lap that never finds a centre leaves those walls in the map. Sim follow L and Sim follow R animate the same decision with the motors never armed, which is how either hand can be run against any maze file with no bench at all — and the companion app’s maze editor is how you get a follower course that is not already in the corpus.

Deliberately absent

  • Diagonals. Heading has exactly four values and the flood is four-connected. Upstream's comments flag this as the thing to expand for diagonals, and warn that the cost calculations need care if you do.
  • Any improvement pass. She searches out and back once, and nothing sends her back out. The measurement now exists — 0.23’s optimistic plan says how much is still to find and which unseen cells lie on the best possible line, which is the proof upstream describes — but the mode that acts on it does not. What is missing is a second objective: flood to the nearest useful unseen cell rather than to the goal, because once a route is known, flooding to the goal just re-drives it. See Ch 12.
  • Front-wall correction. adjustPosition() is return; and stopAtCentre() always coasts to the profiled distance. Both are waiting on the analog front sensor.
  • Sensor-triggered turn entry. turn_smooth can start its curve early on a front-sensor reading, but TURN_THRESHOLD_SS90E is set to 1 000 000 so it never fires. Turns are started purely on distance until the sensors are real.
